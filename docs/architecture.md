# 架构

## 分层与依赖方向

运行时模块按依赖方向分三层，箭头只能自上而下：

```
index.cjs            插件入口，可用全部
   │
   ├── bridge/       传输层：与 Chrome 扩展的本机 HTTP 桥接
   │      │
   ├── core/         领域层：消息片段、会话、队列
   │      │
   └── lib/          通用工具层：不依赖项目内任何模块
```

| 分层 | 允许依赖 | 模块 |
| --- | --- | --- |
| `src/lib/` | 仅同层 | `image.cjs`、`reply.cjs`、`feedback.cjs` |
| `src/core/` | `lib`、同层 | `message.cjs`、`conversations.cjs`、`preferences.cjs`、`queue.cjs` |
| `src/bridge/` | `lib`、`core`、同层 | `web-bridge.cjs` |
| `src/index.cjs` | 全部 | 入口 |

`test/architecture.test.cjs` 会把这张表变成可执行约束，检查四件事：

1. 每个运行时模块都归属已知分层——新增目录时该测试会失败，提醒更新分层表，而不是让规则静默失效。
2. 依赖方向只能自上而下，出现反向依赖即失败。
3. 没有从入口不可达的孤立模块（防重构后留下死代码）。
4. 运行时模块不含 `child_process`、`execFile`、`codexPath`、`CODEX_HOME`、`runner.cjs`。

第 4 条是防止本地 CLI 调用路径回归的哨兵。所有收发都经由浏览器内的在线页面完成，一旦有人重新引入
本地子进程，就必须同时重新处理「不继承 Koishi 密钥」与「Windows 无进程组信号」两件事。

## 模块职责

| 文件 | 职责 |
| --- | --- |
| `src/index.cjs` | Koishi 插件入口。校验配置、装配各模块、注册管理命令与**兜底转发中间件**、把回复发回 QQ。 |
| `src/lib/image.cjs` | 参考图安全下载（协议白名单、SSRF 防护、体积与超时限制、文件头嗅探）与 PNG 文件头解析。 |
| `src/lib/reply.cjs` | 回复片段校验、Markdown 围栏还原、按段落拆分、总量截断。**纯函数。** |
| `src/lib/feedback.cjs` | 面向用户的文案、失败分类、本机路径与凭据脱敏、模型文本转义。 |
| `src/core/message.cjs` | QQ 消息元素 → 有序片段（文本/图片），剥掉开头的 @ 机器人。**纯函数。** |
| `src/core/conversations.cjs` | 网页会话的持久化（名称、归属用户、选中状态、绑定的 ChatGPT 会话编号 `webThreadId`）。 |
| `src/core/preferences.cjs` | 按用户和聊天位置持久化过程通知开关；个人设置优先于 `notifyProgress` 默认配置。 |
| `src/core/queue.cjs` | 任务队列的持久化与串行执行；参考图从暂存目录移入任务目录；终态任务的保留期清理。 |
| `src/bridge/web-bridge.cjs` | 本机 HTTP 桥接服务（默认 127.0.0.1:5141）。管理当前网页任务、令牌校验、进度与结果回传、参考图字节按需下发、回复图片二进制上传。 |

## 数据模型

### 入站片段（QQ → ChatGPT）

```js
{ type: 'text',  text }                    // 用户原文，段内空白与换行保留
{ type: 'image', file, mime, size }        // 任务目录里的 input-<n>.<ext>
```

由 `session.elements` **按原顺序**归一化，只认文本与图片两类元素。`at`、`quote`、`face`、`file`、`card`
等在 `toSegments` 中跳过：`at` 带的是 QQ openid，不转发到外部网页。
`sessionSegments` 另行读取 `session.quote`（或事件中的 quote、内联 quote 子元素），把直接引用中的
文字和图片作为有边界的上下文放在本次消息之前。只附上正文，不附发送人标识，不递归引用；
缺失引用正文时报错，引用和本次消息合计执行输入限制。文件、语音等不支持的元素仍不转发。

提交给网页时，正文 = 所有文本片段按顺序用 `\n` 连接，附件 = 所有图片片段按顺序注入文件选择器。

### 出站片段（ChatGPT → QQ）

```js
{ type: 'text',  text }                    // Markdown 结构以纯文本保留
{ type: 'code',  language, text }          // 单独成段
{ type: 'image', asset, mime }             // 指向任务目录 result-<asset>.png
```

片段顺序即阅读顺序。`lib/reply.cjs` 把连续的文本与代码合并成一个文本批次（代码加围栏），
遇到图片就切段，因此**图片在回复中的位置得以保留**。

## 状态落盘

| 路径 | 内容 |
| --- | --- |
| `data/conversations.json` | 会话名称、所属用户、选中状态及 ChatGPT 会话编号。 |
| `data/jobs/<id>/job.json` | 任务状态、入站片段、ChatGPT 会话编号（`version: 2`）。 |
| `data/jobs/<id>/input-<序号>.<扩展名>` | 该任务下载的参考图片。 |
| `data/jobs/<id>/result-<序号>.png` | 回复中的第 n 张图片。 |
| `data/jobs/<id>/reply.md` | 完整回复文本（含代码围栏），供重发与排查。 |
| `data/jobs/<id>/failure.json` | 失败详情（仅在失败时产生）。 |
| `data/jobs/<id>/dom-probe.json` | 读不到回复时的页面结构快照（仅在失败时产生）。 |
| `data/jobs/<id>/result-probe.json` | 读取回复时附带的页面结构快照（用于事后核对取到的是不是本轮内容）。 |
| `data/web-bridge-token` | 扩展与桥接共用的随机令牌。 |
| `data/web-bridge-port` | 桥接实际监听的端口（`port: 0` 时由系统分配）。 |

任务文件含消息正文与 QQ openid，权限 0600，目录权限 0700。`data/` 已在 `.gitignore` 中忽略。

**旧任务**：生图时代的任务目录没有 `version` 字段，负载结构（`prompt` + `inputImages`）与现在完全不同。
载入时直接跳过、**不删除** —— 那是用户的数据，不该由程序替他决定。

## 数据流

```
QQ 消息（私聊；群聊需 @ 机器人）
  → core/message.toSegments 得到有序片段
  → 图片经 lib/image.downloadImage 安全下载到系统临时目录（0600）
  → queue.enqueue 移入任务目录并落盘 job.json
  → web-bridge 挂起一个待领取任务，/state 暴露正文与图片元数据
  → Chrome 扩展轮询 /state 领取，打开专用标签页
  → 扩展按令牌从 GET /input 取回参考图字节（页面 CSP 不允许页面脚本直连本机），注入文件选择器
  → 填写正文并提交（正文即用户原文，不带任何连接器标记）
  → 扩展读回回复：DOM → 有序片段
  → 回复中的图片经 POST /result-asset 以原始字节上传
  → POST /result 提交片段，桥接校验后落盘并置 ready
  → index.cjs 按片段顺序发回 QQ；超出消息窗口时改为「桥接重发」
```

参考图上传是**闭环**的：45 秒内无法确认附件就明确失败，绝不退化成纯文字请求，
避免把「参考图 + 要求」当成「只有要求」提交。上传只尝试一次。

## 兜底转发

`src/index.cjs` 的转发中间件注册在**所有管理命令之后**，沿用 Koishi 的 `next(fallback)` 语义：

```js
scope.middleware((session, next) => next(() => forward(session)));
```

命令先匹配并产出结果，因此管理命令不会被转发；其余授权消息一律进入 `forward()`。
**这就是「桥接」的全部**：没有意图识别，也没有自然语言分类，没有「用户是不是想画图」这种判断。

命令统一使用 `桥接` 前缀，而不是 `状态`/`取消` 这类短词：通用桥接下每条消息都要转发给 ChatGPT，
短命令名会抢走用户本来想聊天的那句话。

## 授权与群聊

两条入口（命令、兜底转发）都注册在 `ctx.intersect(authorized)` 返回的 scope 上，所以
`authorized` 是唯一闸门，私聊与群聊的差异只体现在这一个函数里：

| 场景 | 条件 |
| --- | --- |
| 私聊 | `platform === 'qq'` 且 `allowedUsers` 命中（`["*"]` 表示全部） |
| 群聊 | `config.groupChat === true` 且 `session.stripped.appel` |

- **群聊默认关闭**。`groupChat` 未设为 `true` 时群聊消息在任何处理之前就被丢弃。
- 群聊**不查 `allowedUsers`**。群里的 QQ openid 是群作用域 id，与私聊 openid 不是同一套；开启后群里任何
  成员 @ 机器人都可使用，回复直接发到发起的那条消息所在频道（即群），群成员均可见。
- **`@` 由 Koishi 保证，插件不自己解析**。`@koishijs/core` 在 guild 会话上执行
  `if (!isDirect && typeof prefix !== 'string' && !appel) return;`，未被 @ 的群消息根本进不了命令管线；
  `session.stripped` 同时给出 `appel` 与已剥掉 @ 及其后空白的 `content`。
- 群聊的 `stripped` **不暴露元素列表**，且 `content` 是 `elements.join('')`（图片元素会变成 `<img/>` 字符串）。
  因此片段化必须直接处理原始 `session.elements`，自己剥掉开头的 `at`，不能用 `stripped.content`。

## 多会话行为

会话按「QQ 用户 + 聊天」隔离：私聊的聊天键是对方用户，群聊的聊天键是群号，因此同一群里每个成员各有一组
独立会话，互相看不到也切不进对方的会话。最多 20 个打开会话。会话编号为 8 位，任务编号为 12 位。
每个会话同一时间仅允许一个待完成任务，不同会话共用全局串行队列。切换会话不会改变已排队任务的归属。
关闭会话前须等待或取消任务；关闭不会删除历史任务和图片。重启后保留会话选择，但不会自动重试中断任务。

**默认就是持续会话**：`Conversations.ensure()` 在第一次收到消息时按需建出「默认会话」，之后一直复用，
所以「没有会话」不是一种正常状态，每条消息都必然带着 `sessionId` 进入队列。这是「接着上一张图继续说」
能成立的前提 —— 用户不需要为了保留上下文先做任何事。

- `桥接新建会话 [名称]`：另建一个会话并切过去，原会话保持打开，可随时切回。
- `桥接重开会话 [名称]`：关闭当前会话再建一个新的。旧会话上下文过长、话题跑偏，或网页侧会话已失效时用它。
- 已删除的 `leave()` / `桥接退出会话` 是「无会话模式」的残留，在持续会话下语义不成立，已移除。

续聊通过服务器保存的确切 ChatGPT 会话编号进入同一网页会话，不接受用户提交任意会话编号。

### 网页会话失效时的自愈

持续会话把「换会话」这件事从用户手里拿走了，所以失效必须能自己恢复，否则一个失效编号会把用户永久卡死。

1. 扩展复用 `https://chatgpt.com/c/<编号>` 时，若地址被重定向回首页（`info.threadId` 变空）且已过 15 秒宽限，
   直接失败并报「会话已不存在或无法打开」，而不是一路空等到桥接超时。
2. 桥接的 `webFailure()` 把它归为独立的 `thread_gone`（不是通用的 `execution_failed`）。
3. `src/index.cjs` 的任务 runner 捕获 `thread_gone` 后调用 `Conversations.unbindWeb()` 解绑该会话，
   下一条消息因此拿到一个全新的网页会话。

注意 `thread_mismatch`（页面停在别的会话上）**不解绑**：它可能只是专用标签页被手动导航走了，
解绑等于白白丢掉用户上下文。

## 失败反馈

只归类**技术**失败：认证失败、额度限制、网页操作未完成、网页会话失效（`thread_gone`）、
网页会话不匹配（`thread_mismatch`）、网络失败、桥接离线/繁忙、超时、读不到回复。

**模型的内容拒绝不是失败**。「抱歉，我不能帮你做这个」在通用桥接里就是它该给的回复，会原样回传给用户；
把它判成 `refused` 再丢掉，用户就看不到自己真正想要的内容。

异常写入任务目录 `failure.json`；任务状态与重发指令都可查询原因。
模型文本作为纯文本转义，隐藏常见凭据、服务 URL 与本机路径（含 Windows 盘符与 UNC 路径）。
不会为失败自动重试。

取消只是请求网页停止生成，是否真正停下取决于浏览器状态，也不保证远端计算立即停止或返还额度。
服务重启后进行中的任务标记 interrupted，不自动重复生成。

## ChatGPT 网页连接器

`src/bridge/web-bridge.cjs` 为本机网页任务服务，`browser-extension/` 为 Chrome 扩展。
它操作已登录的 `https://chatgpt.com/` 普通 Chat 页面，通过页面输入框提交消息，
从最新 assistant 轮次读回内容，不调用未公开聊天接口，也不复制登录 Cookie。

### 复用会话时，轮次基线必须等历史渲染稳定

全新会话的页面是空的，`assistants` / `users` 天然为 0，用「计数增加」判断「本轮回复出现了」是安全的。
**复用已有 thread 时不成立**：输入框先渲染，历史轮次要几秒后才补齐。若在打开标签页的第一次 `inspect`
就采样基线，采到的是 0，历史一渲染出来计数就从 0 变成 1 —— 于是上一轮的图被当成本轮结果回传，
`submitted` 也会被误判为真（哪怕消息根本没提交成功）。

所以续聊时（`current.threadId` 非空）必须等：轮次计数连续两次 `inspect` 不变，且叠加时间下限
（页面上已有 assistant 轮次 ≥8 秒；一个都没有 ≥15 秒，因为「还没渲染出来」和「本来就是空会话」
无法区分，宁可多等）。

收工前再用 message id 确认一次：`data-chatgpt-search-message-ids` 是每条 assistant 消息的稳定标识，
采样时记录、收工时比对，仍是同一条就说明本轮回复还没出现。计数只说明「轮次变多了」，
说明不了「多出来的是我这一轮」，message id 直接回答这个问题。属性缺失时取到空串，这条自动跳过。

### 回合识别：不写标记

旧实现会在提示词里插入一行 `QQ绘图任务 <编号>` 来认出自己发的那条消息。通用桥接下这行字会永久留在
用户的 ChatGPT 会话历史里，与「原样转发」直接冲突，因此已删除。

现在扩展在提交前记录用户轮次数量，用**计数**判断消息是否已经落到页面上；页面渲染差异（markdown、折叠）
只会让文本比对失配，不影响「已提交」的判断。连接器自己的残留草稿靠 `chrome.storage.local` 里的
`draft` 记录识别，不靠正文里的标记；不是自己填的内容一律不动。

### 提交顺序

填写与点击发送分属两个轮询周期：填写后先落盘 `phase: 'sending'`，下一个周期才点击，且点击前会确认
输入框内容仍是自己填的那份。任何一步崩溃都朝「不重复提交」的方向失败。

纯图片消息先按**空正文**提交；只有发送按钮持续不解锁（5 秒）才补**一个空格**。不写标记，也不写任何
用户没说过的说明性文字。

### 回复读取

`serializeReply()` 在最新 assistant 轮次内做 DOM → 片段序列化。**角色标题不是回复内容**：
`<h4 data-conversation-role="assistant">` 里的「ChatGPT 说：」是页面框架，`walk()` 会按
`data-conversation-role` / `data-message-author-role` 属性跳过它 —— 页面不再暴露 markdown 容器时，
序列化会退到整个轮次容器，少了这道过滤，一个还没出图的空轮次也会被读成一条回复。

| DOM | 产出 |
| --- | --- |
| `p` | `text` 段 |
| `h1`–`h6` | `text` 段，前置 `#`×n |
| `ul`/`ol` > `li` | `text` 段，前置 `- ` / `1. ` |
| `blockquote` | `text` 段，前置 `> ` |
| `table` | `text` 段，管道符行 |
| `pre` > `code` | `code` 段，语言取自 `language-*` 类名 |
| `a` | 折进所属 `text` 段，形如 `文字 (https://…)` |
| 行内 `code` | 折进所属 `text` 段，加反引号 |
| `img` | `image` 段，按文档顺序编号 |

**「原始回复」的准确含义**：网页已经把 Markdown 渲染成 HTML，服务端原始字节流拿不到。
这里承诺的是**内容等价**（不摘要、不改写、不丢段落、结构可辨），
不承诺与 ChatGPT 内部 Markdown 源文逐字节一致。

### 图片选择

只在最新 assistant 轮次内查找，且必须通过两道闸门（改这段代码时不要拆掉）：

- `chromeReason(img)`：**先看它是不是在最新回复轮次内部 —— 在就直接放行**。
  位置本身就是最强的证据。只有不在轮次内的图片才继续判断：
  命中 `header`/`nav`/`aside`/`[data-testid*=profile|sidebar]` 祖先，或存在 `main` 却不在 `main` 内
  → 属于页面框架，不是回复内容。账号头像走这条。
- `inUserTurn(img)` / `insideUser(img)`：用户自己那一轮里的图永不作为回复内容。
  用户发出去的参考图走这条（其 `alt` 就是 `用户附件`，`looksGenerated` 也据此拒绝）。

> `outside-main` 这条判断依赖页面结构假设。ChatGPT 一旦把会话渲染到 `<main>` 之外，
> 它会把真正的生成图整批判掉（任务 `e1d8e9675311` 就是这样等满 240 秒的）。
> 所以「在回复轮次内部」必须优先于它 —— 排查时看 `result-probe.json` 的 `chromeReason`。

**全页兜底扫描已删除**。它是「返回账号头像」（任务 `f948b24235f4`）与「返回用户参考图」
（任务 `02c2fa8e036a`）两次事故的根源：ChatGPT 会先渲染空的 assistant 轮次，图片几十秒后才出现，
这段窗口里轮次内没有图，扫描就把页面上其他大图当成了结果。现在找不到就继续等待 ——
**失败方向是「等」，而不是「返回错图」**。

`probeDom()` 里每张图带 `inUser`/`inUserTurn`/`chrome`/`picked`，排查时直接看是哪张被选中、为什么。
读取回复时这份快照随 `/result` 上报，桥接写入 `data/jobs/<id>/result-probe.json`
（`dom-probe.json` 仍只在失败时写）。**遇到「回复不对」先看这两个文件，不要靠猜。**

### 等待与超时

ChatGPT 会先渲染空的 assistant 轮次，长回复还会持续流式输出，所以「文本稳定」不等于回答结束，
**「轮次里有字」也不等于回答结束** —— 空轮次里本来就有「ChatGPT 说：」这类无障碍标题。

完成判定看的是**读出来的内容**（`replyLength` 与 `images`），而不是整个轮次的文本：

- 没有任何可读内容 → 继续等（页面还在渲染）。
- 画廊已经出现但还没有可用图片 → 继续等（图正在画）。
- 轮次里有图片还没加载完（`complete === false` 或 `naturalWidth` 为 0）→ 继续等。
- 页面还在忙（有停止按钮，或出现生成中字样）→ 继续等。

以上都不成立、且序列化结果连续 3 秒没有变化时，才读取回复。
**这一步很关键**：读完之后扩展会 `chrome.tabs.remove()` 关掉专用标签页，
提前收工等于把还在生成的图片连同标签页一起关掉。

240 秒硬上限的判断放在「看起来还在忙」分支之前，避免永远忙的页面把桥接超时耗光；
超时会区分「一直在准备图片但没有产出」与「什么都没读到」，并附页面快照。

已知限制：ChatGPT 因长度截断而出现「继续生成」按钮时，V1 不自动点击（避免循环），
按已得到的内容回传，完整内容仍可在网页上继续。

### 桥接协议 v2

| 端点 | 用途 |
| --- | --- |
| `GET /state` | 领取任务：正文、图片元数据、会话编号、取消标志 |
| `GET /input?id=&i=` | 按令牌流式返回参考图字节 |
| `POST /progress` | 上报阶段（`opening`/`submitted`/`reading`）与会话编号 |
| `POST /result-asset?id=&i=` | **原始字节**上传回复中的第 i 张图片，序号必须连续 |
| `POST /result` | 提交回复片段；桥接严格校验后才接受 |
| `POST /failure` | 上报技术失败与页面快照 |

回复图片单独上传而不是塞进 JSON：base64 会让体积膨胀三分之一，多图必然触顶。
`/result` 的校验包括片段类型白名单、单段与总量上限、图片数量上限，以及
**每个 `asset` 必须已经通过 `/result-asset` 上传过**。不满足则整条拒收，
任务按失败处理，绝不落盘半截回复。

网页无法连接时明确失败，不会回退到其他方式。扩展更新后在 Chrome 扩展管理页点击刷新。

扩展为任务打开专用标签页。处理期间不要编辑、刷新或关闭该页。任务与网页会话编号绑定；
续聊仅进入该用户保存的网页会话。无法确认提交时不会自动再次点击，避免重复提交。
页面验证需用户手动完成，连接器不会处理验证挑战。


### 0.3.0 故障恢复边界

扩展完成读取后先将 returning 阶段与结构化回复写入 chrome.storage.local，再上传图片和结果。桥接网络异常保留该阶段，重试不会再次填写或点击发送；已确认图片索引随阶段持久化。同序号图片仅允许相同字节重传。

服务端 result.json 是结果接收的持久化边界：原子重命名成功后才确认 /result。队列启动会从该文件恢复尚未进入 ready 的任务。QQ 回传另用 job.json 中的 deliveryPlan、deliveryCursor 记录，不把“网页生成完成”与“QQ 全部发送完成”混为一谈。

这不是跨 ChatGPT、文件系统和 QQ 的分布式事务。未确认提交不自动重放；QQ 成功后进程在游标落盘前退出，可能在显式重发时重复最后一段。默认无限保留任务，显式 retentionDays 清理时跳过正在运行或发送的任务。


### 0.3.1 专用网页会话生命周期

一个运行任务拥有一个专用标签页，不复用任意人工标签页。逻辑会话绑定原网页 threadId；DOM 异常不触发解绑或悄悄另起新话题。只有原有 thread_gone 分类继续执行失效会话解绑。

撰写区先排除历史消息与生成写作块等非输入区域，再按 ID、composer 容器、局部发送按钮结构证据确定唯一候选；同等级冲突继续等待，不用空白与字符数猜测。发送、上传和附件确认共享这个区域。DOM 每次注入重新解析，避免长时间持有失效节点。

opening 阶段：核对 URL/thread → 等待既有生成空闲 → 定位输入框 → 必要时一次安全刷新 → 等待历史稳定 → 采样基线 → 上传/填写。缺失/歧义等待 15 秒；一次刷新仍不能解决则报告失败。准备总上限 90 秒，另受服务端 QQ 回复预算约束。刷新仅适用于未触及输入的任务，未知草稿、现有附件或生成状态阻止刷新；恢复计数先落盘。

attaching/filling/filled 阶段：输入框短暂消失时等待恢复，15 秒后仍无唯一候选则保留故障页并失败，不刷新网页。sending/waiting/returning 阶段：不再依赖输入框存在，按提交确认及结果持久化继续；不会由于网页撰写区改变而重发已经提交的请求。
